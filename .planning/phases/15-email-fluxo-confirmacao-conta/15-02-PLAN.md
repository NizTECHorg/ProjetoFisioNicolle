<objective>
Make the SPA side of the confirm-account flow deterministic: the redirect origin is always the production host, and the auth flow is the one that lets GoTrue confirm the account server-side from any device.

Purpose: D-07 bug 1 (link opens localhost) and D-07 bug 2 (click does not confirm) both have a code-side precondition. `env.appUrl` must never resolve to a dev origin, and `flowType` must stay `implicit` so `/auth/v1/verify` can confirm and issue a session without a PKCE code verifier stored on the signup device.
Output: Hardened `src/config/env.ts`, pinned implicit flow in `src/lib/supabase/client.ts`, and a `/auth/confirm` landing that handles the already-used link case.
</objective>

Flow decision locked by this plan (answers D-07 bug 2 explicitly):
The e-mail CTA points at the GoTrue endpoint `{SUPABASE_URL}/auth/v1/verify` (plan 15-03 puts `{{ .ConfirmationURL }}` in the template). GoTrue sets `email_confirmed_at` on that request, server-side, before any redirect — so the account is confirmed even if the SPA never loads. With `flowType: 'implicit'` the signup request carries no `code_challenge`, so `verify` issues the session directly in the redirect hash instead of an auth code that would require a verifier from the original browser. PKCE is NOT restored: it is the approach that rolled the confirmation back when the mail was opened on another device.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build-time env (`VITE_APP_URL`) → `emailRedirectTo` | An attacker-controlled or mistaken build variable becomes the destination of an authenticated redirect |
| E-mail recipient → GoTrue `/auth/v1/verify` | A one-time confirmation token crosses an untrusted transport (inbox, link scanners, forwards) |
| Redirect hash → browser session storage | The implicit flow delivers access/refresh tokens in the URL fragment |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-20 | Elevation of Privilege | Open redirect via `emailRedirectTo` | mitigate | `resolveAppUrl` accepts only `https:` non-local origins and otherwise returns `PRODUCTION_APP_URL`; GoTrue additionally rejects any `redirect_to` outside the Dashboard allow-list (set in plan 15-04) |
| T-15-21 | Spoofing | `window.location.origin` as redirect source | mitigate | Forbidden in `src/config/env.ts` and `src/services/auth.service.ts`; enforced by the negative grep gate in Task 1 |
| T-15-22 | Tampering | One-time token reuse across OTP types | mitigate | `verifyTokenHash` performs a single `verifyOtp` when the URL states its `type`; multi-type retry survives only for type-less URLs |
| T-15-23 | Information Disclosure | PKCE code verifier | mitigate | No verifier is generated or persisted under `flowType: 'implicit'`; no verifier value is written to the repo, logs, or docs |
| T-15-24 | Information Disclosure | Raw Auth error strings in the UI | mitigate | All confirm-callback failures pass through `mapAuthError` before reaching `AuthConfirmPage` |
| T-15-25 | Repudiation | Session tokens in the URL fragment | accept | Inherent to the implicit flow; the fragment is never sent to the server, `detectSessionInUrl` consumes it immediately, and this is the only flow that confirms cross-device |
| T-15-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan; 15-RESEARCH.md records zero recommended installs |
</threat_model>
